# 模型调用方案（信工成员 · 9/27-9/29）

## 1. 模型名称
- 平台：DeepSeek 开放平台；model id：deepseek-flash（默认）/ deepseek-v4-pro
- 位置：src/llm.py 顶部 MODEL_ID，可由 .env 覆盖
- 白名单校验：仅允许上述两个值，写错在启动瞬间报错（不发出请求）
- 版本记录：实际模型标识 + 调用日期写入每次运行的 manifest.json

## 2. API 调用方式
- 协议：OpenAI 兼容；base_url = https://api.deepseek.com
- 参数：temperature=0, top_p=1, max_tokens=1500, response_format={"type":"json_object"}
- 结构化输出：提示词含 "json" 字样并给出输出样例
- 凭据：仅从环境变量/.env 读取；日志与报告一律掩码显示
- 缓存：cache_key = sha256(提示词内容 + 模型标识 + 参数 + 输入数据)，与凭据无关，因此换人换机器命中同一份缓存，评审无需 API Key 即可复现

## 3. 输入文本格式
- 不直接接收 PDF；输入 = 解析器产出的文本片段 + 结构化字段（src/inputs.py）
- 四类输入：科目归一化 / 单位期间识别 / 研报引用匹配 / 异常原因解释
- 硬约束：每段带 chunk_id（页码由程序反查，模型不生成页码）；单段 ≤4000 字符；
  输入中不含待判定的数值结果（模型只做语义匹配，不做数值比较）

| `task` | 中文名 | 用途 |
|---|---|---|
| `match_item` | 科目归一化 | 判断财报原文科目名对应哪个标准科目 |
| `unit_period` | 单位与期间识别 | 判断表头声明的单位、口径、期间类型 |
| `match_claim` | 研报引用匹配 | 判断研报中的句子指向哪个指标 |
| `explain_anomaly` | 异常原因解释 | 在给定候选原因中选择一个 |

### 3.1 输入类型一：`match_item`

```json
{
  "task": "match_item",
  "headers": ["营业总收入", "营业收入", "其中：主营业务收入"],
  "standard_items": [
    {"code": "REVENUE",       "name": "营业收入"},
    {"code": "TOTAL_REVENUE", "name": "营业总收入", "note": "口径可能不同于营业收入，不得自动合并"}
  ]
}
```

| 字段 | 类型 | 必填 | 含义 | 示例 |
|---|---|---|---|---|
| `task` | string | 是 | 任务标识 | `"match_item"` |
| `headers` | list[string] | 是 | 财报原文科目名，原样传入 | `["营业总收入", ...]` |
| `standard_items` | list[object] | 是 | 标准科目清单 | 见上例 |
| `standard_items[].code` | string | 是 | 标准科目编号 | `"REVENUE"` |
| `standard_items[].name` | string | 是 | 标准科目中文名 | `"营业收入"` |
| `standard_items[].note` | string | 否 | 易混淆提示 | 见上例 |

约束：

（1）`headers` 单批不超过 40 条，超出需分批。

（2）`headers` 不传空字符串，不传表格中的数字行。

（3）`standard_items` 为对象列表，不是字符串列表。

（4）`headers` 中不得出现金额。

### 3.2 输入类型二：`unit_period`

```json
{
  "task": "unit_period",
  "chunk_id": "p042_t1",
  "header_text": "合并资产负债表   单位：万元   2025年12月31日   2024年12月31日",
  "candidates": {
    "unit": ["元", "千元", "万元", "百万元", "亿元", "unknown"],
    "scope": ["CONSOLIDATED", "PARENT"],
    "period_type": ["FY", "YTD", "BAL_END", "BAL_BEG", "UNKNOWN"]
  }
}
```

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `chunk_id` | string | 是 | 文本片段编号，页码由程序反查 |
| `header_text` | string | 是 | 表头行的原文，不清洗 |
| `candidates` | object | 是 | 三组候选答案 |

候选取值含义：

| 候选组 | 取值 | 含义 |
|---|---|---|
| `unit` | `元` / `千元` / `万元` / `百万元` / `亿元` | 表头声明的金额单位 |
| `unit` | `unknown` | 表头未写单位或无法识别 |
| `scope` | `CONSOLIDATED` | 合并报表 |
| `scope` | `PARENT` | 母公司报表 |
| `period_type` | `FY` | 全年累计数 |
| `period_type` | `YTD` | 年初至今累计数 |
| `period_type` | `BAL_END` | 期末余额 |
| `period_type` | `BAL_BEG` | 期初余额 |
| `period_type` | `UNKNOWN` | 无法判断 |

约束：

（1）`header_text` 只给表头，不给整页。

（2）长度上限 4000 字符。

（3）`candidates` 必须给全。

### 3.3 输入类型三：`match_claim`

```json
{
  "task": "match_claim",
  "claims": [
    {"claim_id": "c01", "sentence": "公司2025年营业收入为120亿元，同比增长22%"},
    {"claim_id": "c02", "sentence": "归母净利润较上年下降3.5%"}
  ],
  "fields": [
    {"item_code": "REVENUE",   "period": "FY2025"},
    {"item_code": "REVENUE",   "period": "FY2024"},
    {"item_code": "NP_PARENT", "period": "FY2025"}
  ]
}
```

| 字段 | 类型 | 必填 | 含义 | 示例 |
|---|---|---|---|---|
| `claims[].claim_id` | string | 是 | 句子编号 | `"c01"` |
| `claims[].sentence` | string | 是 | 研报原文句子 | 见上例 |
| `fields[].item_code` | string | 是 | 标准科目编号 | `"REVENUE"` |
| `fields[].period` | string | 是 | 期间标识 | `"FY2025"` |

设计说明：`fields` 中刻意不提供 `value`。若提供金额，模型会倾向于自行比较大小时，而其算术结果不可复现。模型只回答"这句话指向哪个指标、哪个期间"，数值比对由程序完成。

约束：

（1）单句截断至 500 字符以内。

（2）单批不超过 40 条。

（3）`period` 写法须与项目统一。

### 3.4 输入类型四：`explain_anomaly`

```json
{
  "task": "explain_anomaly",
  "rule_id": "RP01@v1.0",
  "diff_desc": "研报引用的营业收入数值与财报披露值相差约一个数量级",
  "chunk_id": "p042_t1",
  "quote": "营业收入 1,023,500.00",
  "candidates": ["UNIT_SCALE", "PERIOD_MISMATCH", "SCOPE_MIXED", "VALUE_ERROR", "SIGN_ERROR"]
}
```

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `rule_id` | string | 是 | 触发异常的规则编号（含版本） |
| `diff_desc` | string | 是 | 程序生成的差异描述，不含逐位明细数字 |
| `chunk_id` | string | 是 | 证据所在片段编号 |
| `quote` | string | 是 | 原文片段，不超过 200 字符 |
| `candidates` | list[string] | 是 | 候选原因清单 |

候选原因取值：

| 取值 | 含义 | 典型特征 |
|---|---|---|
| `UNIT_SCALE` | 单位或量级换算错误 | 两侧数值呈 10 的整数次幂关系 |
| `PERIOD_MISMATCH` | 期间错配 | 引用值等于上期或去年同期数值 |
| `SCOPE_MIXED` | 口径混用 | 引用值等于母公司口径数值 |
| `VALUE_ERROR` | 数值引用错误 | 不属于上述三种的数值差异 |
| `SIGN_ERROR` | 正负号错误 | 两侧数值互为相反数 |

约束：模型只能从候选清单中选择一个，返回清单外的值该条作废。

### 3.5 输入侧四条通用硬约束

| 序 | 约束 | 违反后果 |
|---|---|---|
| [1] | 每段文字均带 `chunk_id` | 模型编造页码，证据无法核对 |
| [2] | 单段不超过 4000 字符 | 内容被截断，模型漏读 |
| [3] | 输入中不放待判定的数值答案 | 模型自行算数，结果不可复现 |
| [4] | 科目编号取自 `rules/fields.yaml` | 返回系统不识别的编号，下游取不到数 |

### 3.6 拒收条件

出现任一条，语义侧拒收该输入：

（1）把整份年报或整章正文作为输入。

（2）输入中含金额却要求模型判断对错。

（3）缺少 `chunk_id`。

（4）未提供 `candidates` 却要求模型从固定集合中取值。

（5）科目编号不在 `rules/fields.yaml` 中。

## 4. 返回格式（模型输出契约）

### 4.1 总原则

模型输出先视为不可信数据，必须通过三道校验之后才允许进入程序：

1. 语法校验：输出必须是合法 JSON。
2. 结构校验：字段名、类型、取值范围必须符合本节定义的 schema。
3. 内容校验：引用的证据必须真实存在；报告文字中出现的数字必须在程序给定的范围内。

三道校验都通过，结果才被采用。任何一道不通过，该条结果作废或降级为"需人工复核"，且不中断整体流程。

### 4.2 五类返回的整体关系

模型每次调用只执行一项任务，返回一种结构。五种结构与输入侧四类任务一一对应，另加一种用于生成报告文字。

| 序 | 返回类型 | 对应任务 | 回答的问题 | 在流程中的位置 |
|---|---|---|---|---|
| [1] | `MatchItemOut` | `match_item` | 这个科目名对应哪个标准编号 | 解析之后、取数之前 |
| [2] | `UnitPeriodOut` | `unit_period` | 这张表的单位、口径、期间是什么 | 解析之后、换算之前 |
| [3] | `MatchClaimOut` | `match_claim` | 这句话在说哪个指标的哪一期 | 研报比对的比对之前 |
| [4] | `ExplainOut` | `explain_anomaly` | 这个差额最可能是什么原因 | 规则判为异常之后 |
| [5] | `ReportTextOut` | `gen_report_text` | 把已确定的结论写成一段人话 | 所有判定完成之后 |

五类返回的共同定位：**不产出数值、不生成页码、不识别表格结构。** 它们只提供语义判断与文字表述，数值与位置一律由程序提供。

### 4.3 统一外壳

不论哪类任务，返回值都是一个 JSON 对象，并包含下列公共字段：

| 字段 | 类型 | 必填 | 含义 | 用途 |
|---|---|---|---|---|
| `ok` | bool | 是 | 本次任务是否完成 | 为 `false` 时该条记 `REVIEW` |
| `confidence` | float，0 至 1 | 是 | 对该判断的把握程度 | 用于分流人工复核 |
| `evidence` | object | 是 | 证据 | 供程序校验与报告展示 |
| `reason` | string | 否 | 补充说明 | 人工复核时参考 |

`evidence` 的两个子字段：

| 子字段 | 含义 | 校验规则 |
|---|---|---|
| `chunk_id` | 结论依据的是哪一段输入 | 必须是本次输入中出现过的编号，否则判为编造 |
| `quote` | 该段文字中的原文片段，不超过 200 字符 | 必须能在该片段文本中原样找到，否则判为编造 |

`confidence` 的三档处理：

| 取值区间 | 处理方式 |
|---|---|
| 大于等于 0.80 | 直接采用 |
| 0.50 至 0.80 | 采用，但相关规则判定降级为 `REVIEW` |
| 小于 0.50 | 视为不可用，相关规则记 `NA` |

### 4.4 返回一：`MatchItemOut`（科目归一化结果）

#### 4.4.1 它解决什么问题

同一件事在不同公司的财报里叫法不同，例如"营业收入""营业额""主营业务收入"。而程序需要按统一编号取数、计算差额，因此必须先完成一次"名称到编号"的翻译。

#### 4.4.2 它回答的单一问题

**"这个原文科目名，对应标准清单里的哪一个编号？"**

#### 4.4.3 结构示例

```json
{
  "ok": true,
  "items": [
    {"raw_header": "营业总收入", "canonical_item": "TOTAL_REVENUE", "confidence": 0.95},
    {"raw_header": "营业收入", "canonical_item": "REVENUE", "confidence": 0.95},
    {"raw_header": "其中：主营业务收入", "canonical_item": "", "confidence": 0.20}
  ],
  "evidence": {"chunk_id": "p042_t1", "quote": "营业总收入 营业收入 其中：主营业务收入"},
  "reason": ""
}
```

#### 4.4.4 字段含义

| 字段 | 含义 | 为什么需要它 |
|---|---|---|
| `ok` | 本次翻译是否完成 | 未完成时该批科目整体转人工复核 |
| `items[].raw_header` | 原样回抄输入的科目名 | 程序靠它把结果对回原输入行，防止顺序错乱 |
| `items[].canonical_item` | 标准科目编号 | 下游取数的唯一钥匙；为空表示"确定不了" |
| `items[].confidence` | 该条翻译的把握程度 | 决定这条翻译直接采用还是转人工 |
| `evidence.chunk_id` | 依据的文本片段编号 | 供程序核对，防止编造来源 |

#### 4.4.5 关键取值规则

1. `canonical_item` 只能取输入 `standard_items` 中给出的 `code`；填清单外的值视为无效输出，整条作废。
2. `canonical_item` 为空字符串是合法结果，含义是"无法确定"。程序据此把相关规则记为 `REVIEW` 或 `NA`，不视为故障。
3. `confidence` 逐条给出，不是整批一个值。同一批里可能"营业收入"很有把握，而"主营业务收入"完全没把握，两者必须分别标注。

#### 4.4.6 程序拿到它之后做什么

1. 执行枚举白名单校验，剔除无效编号。
2. 按置信度分流：大于等于 0.80 直接采用；0.50 至 0.80 采用但该规则降级为 `REVIEW`；小于 0.50 视为不可用，相关规则记 `NA`。
3. 把"原文名到标准编号"的映射写回别名表，下次遇到相同名称不再调用模型。

#### 4.4.7 不承担的事

不判断数值、不判断单位、不判断口径、不判断报表归属。

### 4.5 返回二：`UnitPeriodOut`（单位与期间识别结果）

#### 4.5.1 它解决什么问题

金额数值脱离单位没有意义。同一行写着 `1,023,500`，单位是"元"还是"万元"，相差一万倍。同时还要区分是合并报表还是母公司报表，是期末时点数还是全年累计数。这三件事决定程序如何取数、如何换算、能否与另一张表比较。

#### 4.5.2 它回答的单一问题

**"这张表的金额单位是什么、是哪个口径、是哪种期间？"**

#### 4.5.3 结构示例

```json
{
  "ok": true,
  "unit": "万元",
  "scope": "CONSOLIDATED",
  "period_type": "BAL_END",
  "confidence": 0.95,
  "evidence": {"chunk_id": "p042_t1", "quote": "合并资产负债表   单位：万元   2025年12月31日"}
}
```

#### 4.5.4 字段含义与取值范围

| 字段 | 含义 | 取值范围 | 为什么需要它 |
|---|---|---|---|
| `unit` | 表头声明的金额单位 | 见下表 | 决定换算倍数，错一级差 10 倍 |
| `scope` | 报表口径 | 见下表 | 同一科目在合并与母公司口径下数值不同，混用会造成大量假异常 |
| `period_type` | 期间类型 | 见下表 | 时点数与时期数不能互相加减 |
| `confidence` | 把握程度 | 0 至 1 | 单位识别错误代价大，低置信度时宁可不用 |
| `evidence.chunk_id` | 依据的表头片段编号 | — | 单位必须能指回表头原文 |

`unit` 取值：

| 取值 | 含义 |
|---|---|
| `元` | 表头写"单位：元" |
| `千元` | 表头写"单位：千元" |
| `万元` | 表头写"单位：万元" |
| `百万元` | 表头写"单位：百万元" |
| `亿元` | 表头写"单位：亿元" |
| `unknown` | 表头未写单位，或文字残缺无法识别 |

`scope` 取值：

| 取值 | 含义 |
|---|---|
| `CONSOLIDATED` | 合并报表，含子公司 |
| `PARENT` | 母公司报表，仅母公司本身 |

`period_type` 取值：

| 取值 | 含义 | 属于哪类数据 |
|---|---|---|
| `FY` | 全年累计数 | 时期数 |
| `YTD` | 年初至今累计数，如半年报累计 | 时期数 |
| `BAL_END` | 期末余额 | 时点数 |
| `BAL_BEG` | 期初余额 | 时点数 |
| `UNKNOWN` | 无法判断 | 不可参与计算 |

#### 4.5.5 关键取值规则

1. 无法判断时必须返回 `unknown`，不允许推测。理由是单位错误会被放大为整张表全部误判，代价高于标记一次"不可用"。
2. 三个字段都必须落在枚举集合内。返回集合外的值（例如用中文"期末"代替 `BAL_END`）视为无效输出。

#### 4.5.6 程序拿到它之后做什么

1. 校验三个字段取值是否合法。
2. 用 `unit` 做换算，把该表数值折算到统一基准。
3. 把 `scope` 与 `period_type` 写入字段主键，保证只有口径与期间相同的两个数才允许相互比较。
4. 若为 `unknown`，该表数值只记录、不参与任何勾稽计算，并在报告中列为"需人工确认"。

#### 4.5.7 不承担的事

不读取任何金额、不判断表内是否平衡、不做换算（换算由规则程序按 `unit` 执行）。

### 4.6 返回三：`MatchClaimOut`（研报引用匹配结果）

#### 4.6.1 它解决什么问题

研报中"公司 2025 年营业收入为 120 亿元"这类句子，程序无法直接对应到财报的某个字段，因为指标名、期间、口径在自然语言里是隐含的。必须先判断这句话在讲哪件事，程序才知道该拿财报里哪个数来比。

#### 4.6.2 它回答的单一问题

**"这句话指向哪个指标、哪一期？"**

#### 4.6.3 结构示例

```json
{
  "ok": true,
  "matches": [
    {"claim_id": "c01", "item_code": "REVENUE", "period": "FY2025",
     "confidence": 0.88, "reason": "句子指向全年营业收入"},
    {"claim_id": "c02", "item_code": "NP_PARENT", "period": "FY2025",
     "confidence": 0.72, "reason": "提及归母净利润及同比变化"}
  ],
  "evidence": {"chunk_id": "p001_c01", "quote": "公司2025年营业收入为120亿元"}
}
```

#### 4.6.4 字段含义

| 字段 | 含义 | 为什么需要它 |
|---|---|---|
| `matches[].claim_id` | 回抄输入的句子编号 | 程序靠它把判断结果对回原句，报告里也靠它定位 |
| `matches[].item_code` | 指向的指标编号 | 程序用它去字段字典取数 |
| `matches[].period` | 指向的期间 | 区分本期与上期，直接决定取哪一年的数 |
| `confidence` | 把握程度 | 低于 0.80 时该条降级为需人工复核 |
| `evidence.chunk_id` | 依据的句子片段编号 | 供核对 |

#### 4.6.5 关键设计：输出中不含数值

1. 本类输入只给指标与期间清单，不给金额；输出也只给指标与期间，不给对错判断。
2. 原因：一旦把金额交给模型，它会倾向于自行比较大小，而其算术结果不可复现。因此"这句话在说哪件事"由模型回答，"这个数对不对"由程序回答。
3. 分工的后果：模型判断偏了只是"指向了另一个指标"，程序仍会用真实数值做差并给出可复核的结论；若让模型判对错，一旦它算错，整个结论不可追溯。

#### 4.6.6 程序拿到它之后做什么

1. 用 `item_code` 加 `period` 去字段字典取财报数值。
2. 从研报原句中解析被引用的数字，由解析程序完成，不询问模型。
3. 计算相对差异，按容差档位判定状态。
4. 对差额做确定性归因：是否为 10 的整数次幂关系、是否等于上期数值、是否符号相反等。

#### 4.6.7 不承担的事

不判断数值对错、不计算差额、不给出修改建议。

### 4.7 返回四：`ExplainOut`（异常原因解释结果）

#### 4.7.1 它解决什么问题

规则判出"差额超出容差"只是一个事实，报告里需要一句人话说明最可能的原因。这类说明需要理解业务语义；但原因必须可复核，不能每次给出不同说法。

#### 4.7.2 它回答的单一问题

**"在给定的几种可能原因中，这一条最像哪一种？"**

#### 4.7.3 结构示例

```json
{
  "ok": true,
  "cause": "UNIT_SCALE",
  "explanation": "研报数值与财报披露值相差约 10 倍量级，倾向单位换算错误",
  "confidence": 0.80,
  "evidence": {"chunk_id": "p042_t1", "quote": "营业收入 1,023,500.00"}
}
```

#### 4.7.4 字段含义

| 字段 | 含义 | 为什么需要它 |
|---|---|---|
| `cause` | 原因编码 | 报告里用于归类与统计"哪类原因最多" |
| `explanation` | 一句解释 | 写进报告，供人工复核参考 |
| `confidence` | 把握程度 | 低于 0.80 时报告标注"仅供参考" |
| `evidence.chunk_id` | 依据的原文片段编号 | 保证解释有据可依 |
| `evidence.quote` | 原文片段本身 | 报告里展示，供人工快速核对 |

#### 4.7.5 候选取值的确切含义

| 取值 | 含义 | 典型特征 |
|---|---|---|
| `UNIT_SCALE` | 单位或量级换算错误 | 两侧数值呈 10 的整数次幂关系 |
| `PERIOD_MISMATCH` | 期间错配 | 引用值恰好等于上期或去年同期数值 |
| `SCOPE_MIXED` | 口径混用 | 引用值等于母公司口径数值 |
| `VALUE_ERROR` | 数值引用错误 | 不属于上述三种的数值差异 |
| `SIGN_ERROR` | 正负号错误 | 两侧数值互为相反数 |

#### 4.7.6 关键取值规则

1. `cause` 只能从输入给定的候选清单中选择一个，选清单外的值该条作废。
2. 做成"选择题"而非"作答题"，是为了让结论可统计、可复核：程序可以反向核对"选了 `UNIT_SCALE` 的那一条，两侧数值是否真的呈幂次关系"。
3. `explanation` 中不得出现具体金额数字，避免模型自行算数。

#### 4.7.7 程序拿到它之后做什么

1. 校验 `cause` 是否在候选集合内。
2. 用程序侧的确定性归因结果与模型给出的 `cause` 相互印证：一致则记为"已核实原因"，不一致则记为"待人工判定"。
3. 把 `cause` 与 `explanation` 写入异常清单，并在报告中按原因类型汇总计数。

#### 4.7.8 不承担的事

不计算差额、不判定异常与否、不建议具体数值修改。

### 4.8 返回五：`ReportTextOut`（报告文字生成结果）

#### 4.8.1 它解决什么问题

核查结论最终要以人话写进报告。把"规则编号、状态、差额"这类机器语言转成通顺段落，是模型擅长的；但报告是交付物，其中出现一个没有来源的数字，整份报告的可信度就会受损。

#### 4.8.2 它回答的单一问题

**"把这些已确定的结论，写成一段通顺的话。"**

#### 4.8.3 结构示例

```json
{
  "ok": true,
  "text": "本次核查在研报引用维度发现 1 处不一致：研报引用的营业收入与财报披露值相差一个数量级，倾向单位换算错误，建议人工复核原始来源。"
}
```

#### 4.8.4 字段含义

| 字段 | 含义 | 为什么需要它 |
|---|---|---|
| `ok` | 是否生成成功 | 失败时改用模板文字，报告仍能生成 |
| `text` | 报告段落文字 | 直接写入报告 |

#### 4.8.5 关键约束：数字白名单

1. `text` 中出现的每一个数字，都必须是程序事先给定的值。
2. 程序的做法：先准备本次允许出现的数字集合，再用正则从 `text` 中抽取全部数字逐个比对。
3. 出现白名单外的数字，说明系模型自行生成，该段文字整段作废，改用模板生成。

#### 4.8.6 程序拿到它之后做什么

1. 执行数字白名单校验。
2. 通过则写入报告；不通过则回退到模板文字。
3. 无论是否通过，报告中的数值表格、差额、页码一律取自程序结果，不取自模型文字。

#### 4.8.7 不承担的事

不产生任何数值、不产生页码、不判定任何规则状态。

### 4.9 五类返回的取值与校验总表

| 返回类型 | 必填字段 | 取值受限的字段 | 受哪一层校验 |
|---|---|---|---|
| `MatchItemOut` | `ok`、`items`、`evidence` | `canonical_item` | 枚举白名单、证据真实性 |
| `UnitPeriodOut` | `ok`、`unit`、`scope`、`period_type`、`confidence`、`evidence` | `unit`、`scope`、`period_type` | 枚举白名单、证据真实性 |
| `MatchClaimOut` | `ok`、`matches`、`evidence` | `item_code`、`period` | 枚举白名单、证据真实性 |
| `ExplainOut` | `ok`、`cause`、`confidence`、`evidence` | `cause` | 枚举白名单、证据真实性 |
| `ReportTextOut` | `ok`、`text` | `text` 中的全部数字 | 数字白名单 |

### 4.10 三层校验

| 序 | 校验 | 校验内容 | 不通过的处理 | 代码位置 |
|---|---|---|---|---|
| [1] | 枚举白名单 | `canonical_item`、`item_code`、`cause` 是否在候选集合内 | 该条作废，相关规则记 `REVIEW` | `src/validators.py` 的 `check_enum_whitelist()` |
| [2] | 证据真实性 | `chunk_id` 是否来自本次输入；`quote` 是否原样存在 | 结论丢弃，不写入报告 | `src/validators.py` 的 `check_evidence()` |
| [3] | 报告数字白名单 | 报告文字中的数字是否均在给定集合内 | 该段作废，改用模板文字 | `src/validators.py` 的 `check_no_amounts()` |

三层校验分别防止三件事：自行发明编号、编造页码与原文、在报告中写入无来源数字。

### 4.11 校验失败后的处理链路

| 序 | 情况 | 程序动作 | 最终结果 |
|---|---|---|---|
| [1] | 返回内容不是合法 JSON | 提示词补充说明后重试 1 次 | 成功则采用，否则该条记 `REVIEW` |
| [2] | JSON 合法但字段缺失或类型不符 | 同上，重试 1 次 | 同上 |
| [3] | 结构通过但枚举越界 | 直接作废，不重试 | 相关规则记 `REVIEW` |
| [4] | 结构通过但证据不一致 | 直接作废，不重试 | 结论不进报告，相关规则记 `REVIEW` |
| [5] | 报告文字含白名单外数字 | 该段作废，改用模板 | 报告仍生成，仅减少模型润色 |
| [6] | 调用失败，含网络与服务端异常 | 按第 5 节分流表重试或停止 | 单条失败不影响整体流程 |

单条失败不中断整体流程；失败条目标记为需人工复核，其余照常执行。

### 4.12 模型三条禁则

| 序 | 禁则 | 原因 |
|---|---|---|
| [1] | 不产出数值，不输出任何金额数字 | 算术不可靠，数值必须由程序产生 |
| [2] | 不识别表格结构，不判断数字的行列归属 | 行列归属由解析程序确定，以保证确定性 |
| [3] | 不生成页码，只能引用输入中的 `chunk_id` | 页码须由程序反查，否则证据无法核对 |

### 4.13 常见问题

**模型返回空字符串是否算失败。** 不算。"无法确定"是合法答案，程序按置信度将其降级为人工复核。

**`match_claim` 为何不提供金额。** 提供金额会诱导模型自行比较，而其算术结果不可复现。数值比对由程序完成。

**`confidence` 是否可信。** 它仅作为分流信号，用于决定是否需人工复核，不参与任何数值判定。

**校验是否过于严格。** 实测 `match_item` 与 `unit_period` 两类任务在 `temperature=0` 下输出稳定；需人工复核的主要是科目名本身模糊的情形。

**修改 schema 的影响。** 输出结构变更会使已有缓存失效，需重新调用一次，须提前通知组员。

**修改 `PARAMS` 的影响。** 缓存键包含 `PARAMS`，改动后历史缓存全部不再命中。

## 5. 错误处理方式

分流原则：4xx 属"我们的问题，改了再来"（不重试）；429/5xx 与网络异常属"外面的事，等会儿再来"（退避重试）。

| 错误 | 是否重试 | 程序动作 | 触发位置 |
|---|---|---|---|
| 400 格式错误 | 否 | 抛 ProviderError，提示"模型名或参数写错" | src/errors.py NEVER |
| 401 认证失败 | 否 | 抛 ProviderError，提示"Key 无效/带空格/已吊销" | src/errors.py NEVER |
| 402 余额不足 | 否 | 自动降级为离线模式（返回 QUOTA_EXCEEDED_SWITCH_OFFLINE） | src/llm.py |
| 422 参数错误 | 否 | 抛 ProviderError，提示检查参数写法 | src/errors.py NEVER |
| 429 / 500 / 503 | 是 | 指数退避 1s→2s→4s + 抖动，最多 3 次 | src/llm.py |
| 网络超时 / 连接失败 | 是 | 同上，3 次 | src/errors.py |
| 输出非 JSON / 校验失败 | 是（1 次） | 提示词补"只输出 json"后重试一次 | src/llm.py |
| 重试全部失败 | — | 返回 None 与状态串，记录日志，该条标 REVIEW，不中断流程 | src/llm.py |

演练证据（截图见 docs/evidence/）：
- 401_drill.png：认证失败 → 立即停止，不重试
- 400_drill.png：模型名错误 → 平台返回 400，被归类为不可重试错误
- offline_retry.png：断网 → 退避重试耗尽，返回 RETRY_EXHAUSTED:NETWORK，程序不崩

## 6. 不启用联网检索的运行边界

 1.唯一允许出站：api.deepseek.com:443；其余地址由 src/netguard.py 拦截并抛 PermissionError，同时写入 runs/<run_id>/logs.jsonl（allowed=false）。

 2.离线模式（offline=True）不读取凭据、不发起任何网络请求，仅读取本地缓存重放；无缓存时返回 NO_CACHE_OFFLINE。

 3.系统不启用网页搜索、网络爬虫与外部数据库检索；本地检索为本地文件文本匹配，不产生外部请求。

 4.出站记录可机读：每次连接写入 logs.jsonl，含时间、主机、端口、是否放行、用途。
